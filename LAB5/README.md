# Лабораторная работа № 5 — вычисление и сравнение хешей

Программа на C# вычисляет хеши строк и файлов, сравнивает два хеша и измеряет
скорость MD5, SHA-1, SHA-256, SHA-384 и SHA-512. Выполнены все три практических
задания методички. Используется .NET SDK 10 без внешних пакетов.

## Быстрый запуск

Из корня репозитория:

```sh
cd LAB5
dotnet build -c Release
dotnet run -c Release -- self-test
dotnet run -c Release -- demo
```

`demo` создаёт новую папку `results/<дата-время>` с исходным файлом, его копией,
изменённым файлом, результатами сравнения и таблицей замеров на 16 МиБ.
Можно указать свою новую или пустую папку: `dotnet run -c Release -- demo results/my-demo`.
Готовые результаты находятся в [examples](examples), ответы для защиты — в
[CHEATSHEET.md](CHEATSHEET.md).

Если терминал не находит уже установленный в домашней папке SDK:

```sh
export DOTNET_ROOT="$HOME/.dotnet"
export PATH="$DOTNET_ROOT:$PATH"
dotnet --version
```

На машине выполнения SDK 10.0.404 установлен в `~/.dotnet`, PATH настроен
для bash и zsh. В уже открытом bash можно выполнить `source ~/.bashrc`.
Для другого компьютера: [инструкция установки .NET SDK](https://learn.microsoft.com/en-us/dotnet/core/install/linux-scripted-manual).

## Строки и сравнение хешей

```sh
dotnet run -- text MD5 "MySourceData"
dotnet run -- text SHA256 "Привет, мир!"
dotnet run -- compare-text SHA256 "одинаково" "одинаково"
dotnet run -- compare-text SHA256 "MySourceData" "NotMySourceData"
```

Сначала строка переводится в UTF-8, затем `ComputeHash` возвращает массив байтов.
`Convert.ToHexString` выводит каждый байт двумя шестнадцатеричными символами,
включая последний байт и ведущие нули. При сравнении учитываются длина и все байты.
Регистр и пробелы в исходном тексте значимы; нормализация текста не выполняется.

## Задание 1 — хеширование файлов

```sh
dotnet run -- file SHA256 examples/input.txt
dotnet run -- compare-files SHA256 examples/input.txt examples/copy.txt
dotnet run -- compare-files SHA256 examples/input.txt examples/changed.txt
```

Файл читается через `FileStream`, поэтому его не нужно целиком загружать в память.
Поддерживаются любые файлы, включая бинарные и пустые. Хешируются точные байты:
имя файла не влияет на результат, а BOM, пробелы и переводы строк влияют.
Визуально одинаковый текст с LF и CRLF может давать разные хеши.
Исходные файлы не изменяются. Для сохранения результата можно перенаправить вывод:

```sh
dotnet run -- file SHA256 examples/input.txt > results-hash.txt
```

## Задание 2 — выбор алгоритма

| Имя в команде | Длина хеша, бит | Байт | HEX-символов |
| --- | ---: | ---: | ---: |
| MD5 | 128 | 16 | 32 |
| SHA1 | 160 | 20 | 40 |
| SHA256 | 256 | 32 | 64 |
| SHA384 | 384 | 48 | 96 |
| SHA512 | 512 | 64 | 128 |

Имя алгоритма передаётся отдельным аргументом. Регистр не важен, допускаются
обозначения с дефисом, например `sha-256`. Это пять алгоритмов, перечисленных
в методичке; программа не претендует на перечисление всех алгоритмов платформы.
MD5 и SHA-1 оставлены для учебного сравнения: их стойкость к коллизиям нарушена.
Microsoft рекомендует использовать SHA-2 вместо них для новых криптографических
задач: [обзор криптографических алгоритмов .NET](https://learn.microsoft.com/en-us/dotnet/standard/security/cryptographic-services).

## Задание 3 — замеры времени

```sh
dotnet run -c Release -- benchmark examples/input.txt 7
dotnet run -c Release -- benchmark "/путь/к/большому файлу.bin" 7
```

Для сравнения скорости используй файл размером несколько мегабайт: на маленьком
тексте большую долю времени занимают накладные расходы. Готовая демонстрация
использует 16 МиБ и семь повторов для каждого алгоритма.

Методика: один прогрев каждого алгоритма, затем несколько проходов с изменяемым
порядком. `Stopwatch` измеряет открытие файла, чтение и хеширование. Генерация
файла, преобразование результата в HEX и вывод исключены из замера. Все проходы
должны возвращать тот же хеш, что и прогрев. В таблицу выводятся медиана, минимум
и скорость по медиане: `размер_в_МиБ / время_в_секундах`.

После прогрева файл может читаться из кеша ОС. Значения описывают этот компьютер,
его криптобиблиотеку и текущую нагрузку, а не универсальное превосходство алгоритма.
Более длинный хеш не обязательно вычисляется медленнее: важна реализация.

Фактические числа, все отдельные измерения и контрольные хеши:
[examples/benchmark.md](examples/benchmark.md). В сохранённом запуске на Ryzen 5
4600H наименьшее время у SHA-1 (10.705 мс), затем SHA-256 (11.326 мс).
Скорость не означает криптографическую стойкость.

## Исправления методички

Исходные фрагменты и задания сохранены в [Reference/practice-original.txt](Reference/practice-original.txt).
Это фрагменты с пояснениями, а не полный компилируемый проект.

| Проблема | Исправление |
| --- | --- |
| Объявлены `s1SourceData`, `s2SourceData`, но используется `sSourceData` | Согласованные имена переменных |
| `D5CryptoServiceProvider` вместо `MD5CryptoServiceProvider` | Выбор через `MD5.Create()` и другие фабрики |
| Цикл `i < arrInput.Length - 1` теряет последний байт | `Convert.ToHexString` выводит весь массив |
| ASCII заменяет русские буквы на `?` | UTF-8 для строк |
| Старые конкретные классы провайдеров | `MD5.Create()`, `SHA256.Create()` и аналогичные фабрики |

`demo` воспроизводит две логические ошибки: MD5 выводился в виде 30 символов вместо
32, а разные русские буквы «А» и «Б» превращались в одинаковые ASCII-байты.
В последнем случае информация теряется до хеширования; это не коллизия самого MD5.

Теоретические уточнения: хеширование не является шифрованием; коллизии существуют,
поскольку длина результата ограничена. Совпадение хешей не служит математическим
доказательством равенства файлов. Для проверки целостности эталонный хеш должен
быть получен из доверенного источника. Обычный быстрый хеш сам по себе не подходит
для хранения паролей — в LAB4 для получения ключа из пароля использовался PBKDF2.

## Проверки и вывод

В [VALIDATION.md](VALIDATION.md) перечислены фактические проверки. `self-test`
проверяет все алгоритмы по независимым контрольным значениям Python hashlib,
пустые строки, бинарный файл, UTF-8, BOM, сравнение, HEX, ошибки и методику замеров.

Коды завершения: 0 — успех или совпадение хешей; 1 — ошибка входных данных/файла;
2 — неверная команда; 3 — сравниваемые хеши различаются. Код 3 при разных данных
является ожидаемым результатом сравнения.

Вывод: реализованы вычисление и сравнение хешей строк и файлов с выбором алгоритма.
Изменение содержимого обнаруживается сравнением хешей в проведённых примерах.
Скорость алгоритмов измерена на одинаковом файле с прогревом и повторениями.
